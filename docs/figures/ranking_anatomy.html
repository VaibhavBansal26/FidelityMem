How each system ranks a memory

The scoring algorithms behind the LoCoMo and LongMemEval numbers: what BM25 computes, what the dense route computes, how reciprocal-rank fusion merges them, and what FidelityMem adds on top. Every formula and constant is taken from the code in the repository.

1. BM25 (lexical route, and the strongest baseline)

BM25 scores a document by summing, over the query terms it contains, a rarity weight (IDF) times a saturating term-frequency factor that is normalised by document length. Nothing about meaning is involved: a document matches only if it shares the literal (stemmed) words.

Why it wins on LoCoMo. The questions reuse the words of the evidence ("What did Caroline bake for the fundraiser?" against a session that says "bake" and "fundraiser"). Rare words such as names, places and activities have high IDF, so a single shared rare word puts the right session near the top. The dense route cannot exploit that precision.

2. Dense retrieval (vector route)

The embedder maps text to a unit vector; the score is the cosine (dot product) between the query vector and each stored vector. The three embedders used in the project differ only in how the vector is produced.

3. Reciprocal-rank fusion (how routes are merged)

Routes produce lists in incompatible score units (BM25 scores, cosines, graph hop weights), so FidelityMem, the Zep-style and the HippoRAG-style systems merge by rank rather than by score. Each route contributes w / (60 + rank) for every document it lists; the contributions are summed per document.

4. FidelityMem's full ranking pipeline

FidelityMem is BM25 plus five more routes, fused by RRF, then re-ordered by three post-fusion steps. The controller decides which routes are in the pool and at what compression level the store is held; the planner picks weights per query.

6. Where a ranking change could still beat BM25

  • Reranking, not fusion. Use BM25 for candidates and a cross-encoder or LLM reranker to reorder the top 20 to 30. The Haiku reranker tried in Phase 6 gave no gain at K=5 on sessions, but a cross-encoder trained for passage ranking was not tried.
  • Smaller units with session mapping. Retrieve turns or 120-word windows and score a session by its best window. This gives the dense route sharp vectors and keeps BM25's precision. The evidence-first experiment did this only for the context, not for ranking.
  • Route weighting learned from the query log. Today RRF weights are hand-set by query type. The controller could tune the dense weight per dataset the same way it tunes the route pool; on LoCoMo it would learn a weight near zero, on a paraphrase-heavy dataset a higher one.
  • Query-side entity expansion. The graph route already seeds from relations; feeding the bridge entity back into BM25 (the bridged second pass) is what lifts multi-hop. The same trick applied to coreferent names ("my sister" to a known name) is untested.

LongMemEval is the right place to test these, since its multi-session and knowledge-update questions are the ones where keyword overlap is weakest.
