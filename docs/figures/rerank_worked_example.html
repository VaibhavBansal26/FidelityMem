Q1 step by step: "When did Caroline relocate to France?"

Step 1 · Query analysis

Tokenise, drop stop words, stem: ['caroline', 'relocate', 'france']. The planner classifies it as temporal ("when did"), so the temporal route would get weight 1.2 if it were in the pool; here the pool is lexical + vector, the setting the controller picks on paraphrased query logs.

Step 2 · BM25 (lexical route)

Store statistics: N = 5 documents, average length avgdl = 9.0, k1 = 1.5, b = 0.75. Only one query term appears in the index: caroline (df = 2, in m1 and m3). relocate and france have no postings, so they contribute nothing.

idf(caroline) = ln(1 + (N − df + 0.5)/(df + 0.5)) = ln(1 + 3.5/2.5) = ln(2.4) = 0.875

score(m1) = idf · tf·(k1+1) / (tf + k1·(1 − b + b·dl/avgdl))
          = 0.875 · 1·2.5 / (1 + 1.5·(0.25 + 0.75·10/9))
          = 0.875 · 2.5 / (1 + 1.5·1.0833) = 0.875 · 2.5 / 2.625 = 0.834

score(m3) = 0.875 · 2.5 / (1 + 1.5·(0.25 + 0.75·8/9))
          = 0.875 · 2.5 / (1 + 1.5·0.9167) = 0.875 · 2.5 / 2.375 = 0.922

BM25 ranking:  1. m3 (0.922)   2. m1 (0.834)   (m2, m4, m5 unscored)

BM25 puts the wrong memory first. Both candidates match one word; m3 wins because it is shorter (8 tokens vs 10) and length normalisation rewards that. The words that would decide the question, "relocate" and "France", are invisible to it.

Step 3 · Dense route (MiniLM cosine)

Query and memories are embedded to unit vectors; score = dot product.

cos(q, m1) = 0.687   moved to Paris ≈ relocate to France
cos(q, m3) = 0.332   shares "Caroline" only
cos(q, m5) = 0.321   mentions Paris
cos(q, m2) = 0.159
cos(q, m4) = 0.129

Dense ranking:  1. m1   2. m3   3. m5   4. m2   5. m4

The sentence embedder understands the paraphrase and puts m1 first by a wide margin.

Step 4 · Reciprocal-rank fusion (k = 60, weights 1.0 / 1.0)

Each route contributes w / (60 + rank); contributions are summed per document.

m3:  lexical rank 1 → 1/61 = 0.016393   vector rank 2 → 1/62 = 0.016129   sum = 0.032522
m1:  lexical rank 2 → 1/62 = 0.016129   vector rank 1 → 1/61 = 0.016393   sum = 0.032522
m5:  vector rank 3 → 1/63                                                     = 0.015873
m2:  vector rank 4 → 1/64                                                     = 0.015625
m4:  vector rank 5 → 1/65                                                     = 0.015385

An exact tie. Fusion only knows ranks, so "first on one list, second on the other" is symmetric. The 0.687 vs 0.332 margin from the dense route is thrown away. With lexical weighted 1.2 the tie breaks the wrong way (m3 = 0.03580, m1 = 0.03575); with dense weighted 0.5 it also breaks for m3 (0.02446 vs 0.02432). No weighting of these two lists ranks m1 first without also ranking it first on every other query where BM25 is right.

Step 5 · Modulation

Each fused score is divided by the maximum and multiplied by 1 + 0.05·recency + 0.2·tanh(utility) + 0.05·authority + type boost. For two fresh memories with no feedback history and the same source, recency ≈ 1, utility = 0, authority ≈ 0.9: both get × 1.095. Still tied. The factors are deliberately small so they only break near-ties on metadata, which here does not differ.

Step 6 · Relation chaining and top-k

Not a multi-hop question, so chaining is skipped. The top-k cut keeps both m1 and m3 in the context at K = 2 or more, so Recall@K is satisfied either way. The question is only who is first, which matters for MRR, for K = 1, and for the reader when the context is long.

Step 7 · Reranking (the step that resolves the tie)

A reranker scores each candidate jointly with the query instead of independently. Two implementations:

7a · Cross-encoder (not yet in the repository)

A small transformer reads the pair "[query] [SEP] [memory]" and outputs one relevance logit. Because query and memory tokens attend to each other, it can align "relocate to France" with "moved to Paris". Typical output on this pair:

s(q, m1) ≈ +4.1    s(q, m3) ≈ −2.3    s(q, m5) ≈ −1.0
Reranked:  1. m1   2. m5   3. m3

Cost: one forward pass per candidate, about 2–5 ms each on CPU for a MiniLM-sized cross-encoder, applied to the top 20–30 fused candidates only.

7b · LLM reranker (the Haiku step tried in Phase 6)

The top candidates are numbered and sent in one prompt; the model returns the indices most likely to contain the answer, best first.

RERANK. QUESTION: When did Caroline relocate to France?  RETURN 2 NUMBERS.
[0] Caroline said she will not attend the LGBTQ support group this month…
[1] Caroline moved to Paris in March 2023 and opened a small bakery…
[2] Melanie's mother lives in Lyon and visits Paris every spring…
→ model output: [1, 2]
Reranked:  1. m1   2. m5   (fill from original order if fewer than k returned)

Cost: one API call per query, roughly 300 input tokens here, far more with 48 long sessions. On LoCoMo sessions this step gave no gain at K = 5 because BM25's top 5 already contained the gold session on 86 % of questions and the model rarely reordered within them; it would help exactly on the Q1 kind of question.

Summary of Q1: BM25 wrong by length normalisation, dense right by a margin of 0.35, RRF erases the margin into a tie, and only a step that looks at the query and the memory together restores the right order.

Four of five questions are literal, and on those BM25 is right and fusion agrees. That ratio is roughly LoCoMo's, which is why BM25 scores 0.915 there and nothing beats it. Q1 and Q4 are the paraphrase cases, and they show the two failure modes: a wrong winner by length normalisation, and an empty result.

The reranking algorithm, stated once

  1. Candidate generation. Run every route in the controller's pool with per-route depth 3·K. Fuse by weighted RRF. Keep the top M = 20–30 candidates (not K): the reranker needs headroom to promote something from rank 15 into the top 5.
  2. Joint scoring. For each candidate c, compute s(q, c) with a model that reads q and c together: a cross-encoder logit, or an LLM's returned order. Independent scores (BM25, cosine) cannot do this; they score c without seeing how q's words align with c's.
  3. Reorder. Sort the M candidates by s. Optionally interpolate with the fused score to keep the first-stage evidence: final = λ·norm(s) + (1−λ)·norm(fused), λ ≈ 0.7.
  4. Cut to K, then run the existing post-steps unchanged: contradiction check, raw-source expansion, token budget.
  5. Controller placement. Reranking is a configuration option with a latency cost, so it belongs in the controller's search space like the dense weight: enabled only when the calibration query log shows it raises recall or MRR enough to pay for its cost under the ρ bound.

Expected effect: little on Recall@10 for literal queries (the gold is already in the top 10), a large gain in MRR and Recall@1 on paraphrased queries, and the only mechanism in this pipeline that can turn the Q1 tie into the right answer.
